# S2 — the attestation report itself: what one field binds

**Date:** 2026-11-21 · **Seat:** security · **Unit:** S2 (primary source)
**Artifact:** `report_data_test.py` + `report-data-test.txt`

The unit reads the report fields and policy bits, then writes one plain-language
test for one field and runs it. The field chosen is `REPORT_DATA` (offset
`0x50`, 64 bytes) because it is the only field a requester chooses, and because
`tools/snp_report.py` parses it at line 135 and asserts nothing about it.

## The machine measured

HQ's own guest, `https://odile.fyi`, release `2026.11.2`:

| Field | Value | Plain sentence |
|---|---|---|
| version | 5, 1184 B | a rev-1.58 report |
| measurement | `e99728ef…fbc` | the launch digest of firmware + kernel + initrd + cmdline |
| policy | `0x30000` | SMT allowed, DEBUG clear, no migration agent, ABI floor 0.0 |
| platform_info | `0x5` | SMT on; ECC_EN set; TSME off |
| flags | `0x0` | VCEK-signed, chip id unmasked, no author key |
| VMPL | `0` | a guest asked for this report (a host-asked one reads `0xffffffff`) |
| report_id | `186313cb…d1d0` | per guest; identical in two fetches seconds apart |
| REPORT_DATA | `odile:<24 random bytes>` | the machine's label, not the visitor's nonce |

The full report verifies against AMD's KDS and chain:
`verify-live-report.txt` — `vcek PASS`, `chain PASS` (ARK SHA-256
`69:d0:63:b4…0b:cd`), `cpu binding PASS`, `signature PASS`, `policy PASS`,
`tcb PASS` (`committed snp=29 >= 27`), `report PASS`, exit 0.

## Source, read 2026-11-21

AMD, *SEV Secure Nested Paging Firmware ABI Specification*, publication 56860,
revision 1.58, May 2025 —
<https://www.amd.com/content/dam/amd/en/documents/developer/56860.pdf>.

Quoted, because the field names in code are not the argument:

- §7.3: “The message contains data provided by the guest in REPORT_DATA to be
  included in the report; the firmware does not interpret this data.”
- Table 22: `REPORT_DATA 511:0` — “Guest-provided data to be included in the
  attestation report.”
- Table 23, `50h`: “If REQUEST_SOURCE is guest provided, then contains
  Guest-provided data, else host request and zero (0) filled by firmware.”
- Table 23, `30h` `VMPL`: a guest request carries 0–3; a host request carries
  `0xffffffff`.
- Table 23, `90h` `MEASUREMENT`: “The measurement calculated at launch.”
- §7.3: the firmware “generates a report ID for each guest that persists with
  the guest instance throughout its lifetime”.
- §4.3: “The guest owner provides the guest policy to the firmware during
  launch… The policy cannot be changed throughout the lifetime of the guest.”
- Table 9: bit 19 `DEBUG`, bit 18 `MIGRATE_MA`, bit 17 “Reserved. Must be
  one.”, bit 16 `SMT`.

## The exercise

`./report_data_test.py` takes no arguments, runs as root on this guest, and
prints four sentences plus a verdict. Its output is kept verbatim in
`report-data-test.txt`.

1. **The field follows the caller.** A report fetched with 64 bytes of ours
   carries them back byte for byte: the caller chooses `REPORT_DATA`, not the
   machine.
2. **Only that field is per request.** Two fetches seconds apart differ only
   inside `0x50–0x90` (and the signature over it); `report_id` is the same.
   The measurement is the launch digest in both.
3. **The served report answers HQ.** `https://odile.fyi/attestation` (refreshed
   by `odile-attest-refresh.timer`, `OnCalendar=*:0/5`) carries
   `odile:<random>` generated by `attest.py` at fetch time — not a nonce the
   visitor sent. A copy of it verifies identically a week later.
4. **The check bites.** One flipped bit in a copy of the report makes the same
   test say “a value this caller did not send”, so the assertion is not
   vacuous.

## Findings

**F1 — `REPORT_DATA` is the freshness contract, and `/attestation` does not
offer one to the reader.** The signed report is genuine and, on HQ, refreshed
every five minutes (`served-roll.txt`: `fetched_at` 06:45:13Z → 06:50:01Z with
a new `odile:` label each time); but `fetched_at` lives *outside* `report_b64`
and outside the signed 672 bytes (`served-document.txt`: `fetched_at is inside
report_b64: False`), so a replay can carry any `fetched_at` its server likes.
The honest sentence for the page is “the report answers the refresh timer, not
your request”, unless the endpoint accepts a caller’s nonce. No public sentence
is false today: `CLAIMS.md` says only “The report refreshes every five
minutes”, and the page does not claim liveness.

**F2 — a parsed field that is never asserted is not verified.**
`tools/snp_report.py:135` stores `self.report_data`; nothing reads it, prints
it, or checks it, so the CLI cannot show a reader that the 64 bytes are HQ's
label. The smallest fix is a printed line plus one sentence in the check; it is
product code, so it needs a card, not this session.

**F3 — the policy is the launcher’s, not the user’s.** §4.3 says the guest
owner supplies the policy at launch and it is fixed for the guest’s life. On
Odile the launcher is the provider, so `DEBUG` clear and `MIGRATE_MA` clear are
hardware-enforced facts about *how the provider launched this guest*, not
choices the user made. That is still worth having; it is not the same sentence.

**F4 — bit 17 is “must be one”, not “must be zero”.** `0x30000` is correct for
rev 1.58; a checker that encodes the older reserved-bits reading rejects a
correct report. Test the bit number and the revision you read, not a remembered
“reserved”.

**Observation, not changed here:** `check_header` rejects VMPL `0xffffffff`
with “a report from a lower-privilege layer is not the guest”; the rejection is
right, but that value means *host-requested*, not a lower VMPL. Cosmetic; it
belongs to `tools/snp_report.py`.

## Residual risk

**R-S2-1 — the served report cannot bind a visitor.** Accepted for alpha.0
because no public sentence claims liveness. Owner: security. Revisit at the M2
tenant verifier, where a user’s browser can supply the 64 bytes; the fix is an
endpoint that accepts a nonce and calls `SNP_GET_REPORT` per request, or a page
sentence that names the timer. Review date: 2026-12-19.

## Rerun

```sh
# From the repository root:
cd docs/ops/evidence/2026-11-21-security
./report_data_test.py --served https://odile.fyi/attestation   # 4 checks, exit 0
./report_data_test.py --served /var/lib/odile/attestation.json # same bytes, same verdict

# The full report, not only its REPORT_DATA field:
cd ../../../..
/usr/bin/python3 -c "import json,base64; open('report.bin','wb').write(base64.b64decode(json.load(open('/var/lib/odile/attestation.json'))['report_b64']))"
/usr/bin/python3 tools/snp_report.py report.bin --amd-dir tests/fixtures/amd
```

`report.bin` is the signed 1184-byte report, `report_b64` from the served JSON
base64-decoded. It is not committed: it carries the chip id, which names the
silicon and which the leak gate classes as machine identity; the transcript
elides every 64-byte value to its first and last 8 hex digits. The AMD KDS
answered the same VCEK in two encodings on two fetches of this session (PEM and
DER), so the printed SHA-256 of the raw body differs between runs; the chain,
the CPU binding and the signature are what the check asserts, and all three
verify both times.
