# M1 benchmark — latency, tokens, RAM, disk, cost (ODL-206)

**Card:** ODL-206 · **Machine:** `odl-fake01` — Servury Blackbox **Plus**
(`0badc0de`), 4 vCPU (EPYC-v4) / 8 GB / 100 GB, SEV-SNP, the custom measured image of
ODL-454/ODL-472 (release `2026.11.11-8`, measurement `9f01725a…`), tenant
booted 2026-11-12T14:43:54Z (`docs/evidence/m1-tenant.md`).
**Run:** 2026-11-12T18:33–19:14:54Z, from HQ, no operator login.
**Software measured:** Hermes 0.23.0 (gateway + Webapp) on the tenant; Chromium
150.0.7871.181; node v26.12.1 / npm 12.0.2; Python 3.14.9; `agent.reasoning_effort:
high` (the tenant's shipped config).

**Why this document exists.** M1 has to replace opinions with numbers before
committing to a plan size and a model. This is the measurement, the spread and
the two decisions it supports: **Core or Plus**, and **DeepSeek V4.1 Flash or
GLM 5.3 Flash**.

## 1. Method

**The surface is the product surface, and the operator is keyless.** The tenant
has no operator SSH key (`ssh -F /dev/null -o BatchMode=yes root@203.0.113.87
true` → `Permission denied (publickey)`, exit 255, §10 of `m1-tenant.md`). The
benchmark therefore drives the tenant through its **own Webapp session** — the
same path the user takes: `POST /auth/password-login` (provider `basic`, user
`tenant`) → `POST /api/auth/ws-ticket` → `wss://odl-fake01.odile.fyi/api/ws`.
Each turn is one `prompt.submit` JSON-RPC request; the client records the time
at submit and again at the `message.complete` event for that turn. The
Webapp, the gateway, the meter and the tools are the ones the user runs; the
only thing outside the product is the measurement client.

**The task** — five turns, every one of them requiring a tool (`write_file`,
`terminal`, directory listing and file read), run in a fresh directory per run:

| Turn | Prompt | Tool it needs | Correct answer |
|---|---|---|---|
| 1 | Create a file `notes.txt` in the current working directory containing exactly the line `alpha`. Reply with only: done | `write_file` | `done` |
| 2 | Append the line `beta` to `notes.txt`. Reply with only the file's size in bytes. | `terminal`/edit | `11` |
| 3 | Run `date -u +%FT%TZ` and append its output as a third line to `notes.txt`. Reply with only the timestamp. | `terminal` | a UTC timestamp |
| 4 | List the files in the current directory. Reply with only their names separated by commas. | `terminal`/list | `notes.txt` |
| 5 | Read `notes.txt` and reply with only the number of lines it contains. | file read | `3` |

Three runs per model, each in its own directory and its own session:
**15 turns per model, 30 turns total**. Every turn reported `outcome:
completed`, used at least one tool, and returned the correct answer (turn 2
answered `11 bytes` on one run — correct, not a failure). The model is switched
per session (`session.create` `model`/`provider`), so both models ran on the
same machine, the same gateway and the same meter.

**Tokens and money come from the machine's own accounting.** After each
session the benchmark reads the tenant's `~/.hermes/state.db`
`session_model_usage` (Hermes's provider usage: `api_call_count`,
`input_tokens`, `output_tokens`, `cache_read_tokens`, `estimated_cost_usd`) and
NEAR's published prices from the meter's `/v1/models` listing (the meter reads
them from `cloud-api.near.ai`). The row is the tenant's, not the client's
estimate.

**RAM and disk are sampled on the tenant.** `ps -eo rss=` summed every 2 s;
`free -m`; `df -B1 /` before and after the build; `du -sh` for the artefacts.
The load is the realistic one the plan decision names: the 30 turns, one npm
install + build, and a headless Chromium held open, followed by an idle soak to
look for growth.

**NEAR prices used** (from the meter's live `/v1/models`, 2026-11-12):

| Model | input $/M | cached input $/M | output $/M |
|---|---:|---:|---:|
| `deepseek-ai/DeepSeek-V4.1-Flash-1017-abliterated` | 0.30 | 0.006 | 1.20 |
| `z-ai/glm-5.3-flash` | 0.08 | 0.012 | 0.50 |

## 2. Numbers

### 2.1 Turn latency — one five-turn task, three runs

`n = 15` turns per model (3 runs × 5 turns). Latency is wall-clock submit →
`message.complete`, including tool execution and streaming.

| Model | p50 s | p95 s | min s | max s | mean s | per-run p50 (r1 / r2 / r3) |
|---|---:|---:|---:|---:|---:|---|
| DeepSeek V4.1 Flash | 6.41 | 32.63 | 3.23 | 40.16 | 10.57 | 6.77 / 6.78 / 5.75 |
| GLM 5.3 Flash | 3.75 | 9.52 | 1.76 | 9.86 | 4.72 | 3.44 / 3.59 / 4.03 |

The DeepSeek p95 is set by two cold-start outliers in run 1 (29.41 s and
40.16 s — the first turn after the model had been idle, and the turn that made
two tool calls); its run 2 and run 3 p50s (6.78 s, 5.75 s) are close to run 1's
median. GLM's worst turn was 9.86 s. The spread is in `m1-raw.csv`.

### 2.2 Tokens and cost per five-turn task

Per session, from `session_model_usage` (the `task` row; the post-task
self-improvement review is reported separately):

| Model | run | API calls | prompt tokens | of which cached | uncached input | output | cost (USD) |
|---|---:|---:|---:|---:|---:|---:|---:|
| DeepSeek | 1 | 11 | 152,361 | 140,096 | 12,265 | 570 | 0.005204 |
| DeepSeek | 2 | 11 | 152,049 | 140,928 | 11,121 | 492 | 0.004772 |
| DeepSeek | 3 | 10 | 137,240 | 126,336 | 10,904 | 350 | 0.004449 |
| GLM | 1 | 10 | 131,699 | 104,704 | 26,995 | 257 | 0.003545 |
| GLM | 2 | 10 | 131,102 | 111,616 | 19,486 | 188 | 0.002992 |
| GLM | 3 | 12 | 161,039 | 146,176 | 14,863 | 409 | 0.003148 |

The prompt is dominated by the agent's system prompt and the growing
transcript; the uncached fraction is small because the provider's cache hit is
high on the repeated prefix. **Per task the median is $0.00477 (DeepSeek) and
$0.00315 (GLM)** — GLM is ~35% cheaper even though it sends more uncached
input, because its input rate is 3.75× lower.

**Post-task self-improvement review.** Hermes runs a background
"self-improvement review" after a session. It fired on 5 of the 6 sessions and
is real inference spend: DeepSeek 1–7 calls, **$0.001263–$0.009286** per
session (mean $0.005615 over the three that fired); GLM 2–14 calls,
**$0.001299–$0.005914** (mean $0.002404 over the three, one did not fire).
Add it to the task cost when budgeting a day.

### 2.3 Cost per active day

An **active day** here is 30 turns — six five-turn tasks — of the kind
measured above. The figure is tokens × NEAR's published prices, measured, not
modelled:

| Model | six tasks | six reviews (measured mean) | active day |
|---|---:|---:|---:|
| DeepSeek V4.1 Flash | $0.0289 | $0.0337 | **$0.0625** |
| GLM 5.3 Flash | $0.0194 | $0.0144 | **$0.0338** |

Against a $100/day budget this is not the binding constraint: ten tenants
at 30 turns a day each cost **$0.34–$0.63/day** in inference on this evidence.
A day of 60 turns doubles it.

### 2.4 RAM and disk — the plan-size number

The load: the gateway (`hermes`), the Webapp, the meter, the first-visit and
manifest services, a headless Chromium (691–767 MiB RSS) held open, one
`npm install` + `vite build` (155 MB of `node_modules`), and the 30 agent
turns. Sampled every 2 s.

| Metric | Peak | Where |
|---|---:|---|
| Sum of all tenant process RSS | **1.26 GiB** (1,322,240 kB) | run phase, 6.7 min (`m1-soak.csv`) |
| Sum of all tenant process RSS | **1.64 GiB** (1,720,196 kB) | 30-minute soak with Chromium open, peak at +15–19 min (`m1-soak.csv`) |
| `memory.current` for `odile-agent.service` | 1.18 GiB (1,264,058,368 B) | `systemctl show` during the soak |
| Chromium RSS | 691–767 MiB | headless, `about:blank` |
| `hermes` gateway RSS | 329–352 MiB | throughout |
| Memory used (`free -m`) | 1.49 GiB of 7.31 GiB | peak, soak |
| OOM kills | **0** | no `oom`/`out of memory` line in the kernel journal |
| Swap | 0 | `free -m` |

**Disk (Chrome + one build included):**

| Item | Bytes |
|---|---:|
| root filesystem total | 7,804,604,416 (7.27 GiB) |
| used before the build | 6,098,571,264 (5.68 GiB) |
| `npm install` + `vite build` delta | +162,377,728 (155 MiB) |
| Chromium already installed in the image | 366 MB (`/usr/lib/chromium`) |
| free after the build | 1,120,673,792 (1.04 GiB, 85% used) |
| free after the whole run | 949,305,344 (0.88 GiB, 88% used) |

The **disk**, not the RAM, is the tight resource: the image's 8 GiB root is
83% full at handoff and one npm build plus Chromium leaves ~1 GiB. `~/.hermes`
alone is 3.5 GB (the Hermes toolchain: node 230 MB, python 260 MB, ffmpeg
438 MB). An 8 GiB Core root would fit this workload but has little headroom.

## 3. Recommendation

**Plan: Core.** The measured peak with the browser and one build is **1.26 GiB**
(run phase) / **1.64 GiB** (soak) against the plan decision's 3.0 GB of
Core's 4 GB, with zero OOM kills. The decision rule therefore fires for Core.
The caveat is the disk: if Core ships the same 8 GiB root, the image is 85%
full after one build.

**Model: GLM 5.3 Flash.** On the same machine, same meter and same five-turn
tool task it is **1.7× faster at p50** (3.75 s vs 6.41 s), has a **tighter
tail** (p95 9.52 s vs 32.63 s, driven by DeepSeek cold starts), **~35% cheaper
per task** ($0.00315 vs $0.00477) and **~46% cheaper per active day** ($0.0338
vs $0.0625 including the measured review overhead), and it completed every
turn with the correct tool use. DeepSeek's one advantage in this run is not
visible: both models answered every turn correctly.

**What would change it.**

- **Core → Plus:** a five-day peak RSS above **3.0 GB** (a leak adding
  ~1.4 GiB over five days), or **one OOM kill**. The 30-minute soak shows no
  monotonic growth (bucketed means 1.28–1.36 GiB; last bucket 1.35 GiB against
  the first 1.28 GiB), but five days is ODL-207's observation, not this
  card's.
- **GLM → DeepSeek:** a quality regression on real work. This harness is a
  simple five-turn file task; it measures tool reliability and latency, not
  reasoning quality. Two named checks would flip the model: GLM failing a
  multi-step tool task that DeepSeek completes, or GLM's answer quality on the
  first five dogfood tasks (ODL-207) being visibly worse. A NEAR price change
  that erases the 3.75× input-rate advantage would also re-open it.
- **Disk:** an 8 GiB root with a second npm build or a larger Chromium cache
  runs out (1.04 GiB free after one build here, 0.88 GiB after the full run); if Core's disk is 8 GiB, the
  plan needs the disk cut named, not the RAM.

## 4. Caveats and what is not measured

1. **Five-day peak RSS is a proxy here.** This card measures a 6.7-minute load
   phase plus a 30-minute soak (`m1-soak.csv`); the five-day peak is ODL-207's
   five-day dogfood log. No upward drift in the soak is evidence against a
   leak, not proof.
2. **The task is a floor, not a typical day.** Five short tool turns in a
   fresh directory; no long research task, no image, no second agent. Tokens
   per *typical* task depend on the user; the per-turn token counts in §2.2
   scale linearly with the transcript.
3. **DeepSeek's p95 includes two cold-start outliers** (29.41 s, 40.16 s) in
   run 1; with them excluded its p95 would be ~11.75 s. They are in the raw CSV
   and in the p95 above.
4. **The self-improvement review is not deterministic.** It fired on 5 of 6
   sessions with a 7× spread; the day cost in §2.3 uses the measured mean and
   names the range.
5. **The harness leaves state on the test tenant:** six sessions, a
   `bench/` script directory, one npm build and Chromium runs; the
   self-improvement review created a `cli-file-ops` skill on the tenant. The
   machine is the test tenant Savio provided (ODL-332), not a user's.

## 5. Raw data

- `docs/benchmarks/m1-raw.csv` — one row per turn (30 rows): model, run,
  turn, elapsed seconds, outcome, tools used, answer, cumulative calls,
  prompt/input/cached/output tokens.
- `docs/benchmarks/m1-soak.csv` — the whole RAM observation, one row every
  2 s: the run phase (30 turns + the npm build) followed by the 30-minute soak
  with Chromium open. Columns: timestamp, sum of tenant process RSS (kB),
  memory used (MB), `hermes` RSS, Chromium RSS.

## 6. Reproduction

From HQ, with the tenant's sign-in (the test tenant's, held with the ODL-332
run record; no secret is in this document):

```
POST /auth/password-login  {"provider":"basic","username":"tenant","password":"<test sign-in>"}
POST /api/auth/ws-ticket
wss://odl-fake01.odile.fyi/api/ws?ticket=<ticket>
  session.create {"cwd":"/home/tenant/bench/m1/work-…","model":"z-ai/glm-5.3-flash","provider":"custom"}
  prompt.submit {"session_id":"…","text":"<turn prompt>","submission_id":"<uuid>"}
  … wait for the message.complete event; repeat five times
  shell.exec    {"session_id":"…","command":"df -B1 / | tail -1"}
```

The tokens are then read from `~/.hermes/state.db` (`session_model_usage`),
the prices from `http://127.0.0.1:8010/v1/models` on the tenant, and the RSS
from the `ps -eo rss=` sampler in `m1-soak.csv`. The client is standard
library plus `websockets`; it lives outside the repo with the run scratch.
