# SPEC — The first run in six acts

**Superseded, 10 November 2026:** Acts A and D (the pasted boot key and the
terminal ceremony) are replaced by `docs/product/DECISION-strict-no-cli.md`.
The reserve, ready, first-run and hub acts stand; the hub loses its unlock
command. Do not build Acts A/D from this spec.

**Status:** M1 spec, build split for M3 · 9 November 2026 · Product lead
**Card:** ODL-406 · **Decision:** `docs/product/DECISION-first-run-six-acts.md`
· **Findings:** `docs/product/REVIEW-UX-2026-11-07.md` §6.2–§6.5
**Question:** what is the product flow a tenant returns to, as opposed to the
twelve-screen story that teaches the trust model?
**Short answer:** six acts, four product surfaces — claim, reserved, ready, hub —
plus the Webapp's first session. The access model, the price and every public
claim are unchanged. This card edits no code; the split below is seeded after
the M1 gate.

---

## 1. The decision

The 12-screen prototype stays as the **teaching artifact** (`prototype/`,
accepted 14/14). The product's information architecture is six acts:

| # | Act | Surface | One primary action | The moment it carries |
|---|---|---|---|---|
| A | Invite + claim | `odile.fyi/claim?t=<invite token>` (HQ, no JS) + the invite email | **Claim my machine** | The key is the only key; the fingerprint and second copy |
| B | Reserve | the same URL, reserved state; the payment link in the email | **Open the sample report** (V0.1 alpha); **Pay $49/month** from M4 (`ODL-241`) | Price before commitment; a sample proof before payment |
| C | Build + ready | `odile.fyi/ready/<slug>` (HQ, no JS) + the ready email | **Run the verifier** | The wait is a state; the four steps and the three gaps |
| D | Ceremony | the `/ready` checklist, four copy blocks; the user's terminal | **Run the verifier** (step 1; **Open the terminal** is its link) | Verify → encrypt → unlock → install → recovery file |
| E | First run | the Webapp's first session | **Open today's brief** | Five questions, a real brief, one scheduled job |
| F | Your machine | `https://<slug>.odile.fyi/#/hub` (Webapp plugin) and the pinned “Your machine” session (C3) | **Ask the agent** | One bookmarkable home: workspace, proof, reboot, support |

Twelve screens become **four product surfaces — claim, reserved, ready, hub —
plus the Webapp's first session**. The six terminal sessions become **five
sessions inside four steps** on one page. The number of commands is not the
promise; the number of decisions is.

**Milestone.** The structure is the M1 information architecture; the cards that
build it are **M3**. They cannot be M1: the claim page depends on
`ODL-220` (M2 claim automation), the ready page on `ODL-202`/`ODL-332` (the M1
machine tail), the first run on the M3 installer (`ODL-387`), and the hub on
`ODL-387`/`ODL-240`. Marking them M1 would be a milestone lie. The M1 gate
decides whether they run at all (§9). The split is the M1 flow **seeded in M3
by dependency**: if the machine tail and `ODL-220`/`ODL-221` land by
22 November, the M1 gate may pull C1–C5 into M1 without a body change;
otherwise they run in M3.

**What does not change.** The boot key is generated by the user at claim and is
the only key in the measured command line; the Odile sign-in is set at install
and hashed on the guest; there is no HQ account, no operator key, no escrow; the
hub lives inside the Webapp behind the existing sign-in; the data path is
unchanged. The privacy-first test is §10.

## 2. Why, in evidence

- `REVIEW-UX-2026-11-07.md` §6.2: PF-01..PF-08 — twelve screens, six terminal
  sessions (fourteen commands), the proof at screen 10 after payment, no
  returning-user home, the densest screen at Ready, five questions before value,
  acquisition and first run disconnected, support as a page, and the Webapp
  saying `HERMES AGENT`.
- The live demo, 9 November 2026 05:12 UTC: `/judge` → sign-in → the seeded
  “Start here” session in about 15 s, with the three proof actions and the
  `/verify` link. The demo proves that a three-step path works; the tenant flow
  is still the linear story.
- M1's exit is “Savio completes claim → ceremony → install → first sign-in in
  under 30 minutes” (`docs/MVP-V0.1.md` §9). The linear flow spends that budget
  on narration. M3's exit is “three outsiders complete the ceremony and install
  with no hand-holding; one runs the verifier; one reads `/verify` and
  understands it”; that is the six acts' acceptance.
- The metric is unchanged: week-4 retention of **activated** users — claimed,
  ceremony, installed, first-run ritual, one scheduled job delivered
  (`docs/backlog.yaml` meta). The six acts remove the five-question
  interrogation and give the returning user a home; they do not widen
  activation.

## 3. The six acts, screen by screen

Rules for every HQ page: no `<script`, no cookie, no third-party request, one
primary action, readable at 390 and 1440, errors in place. Native
`<details>` carries progressive disclosure; there is no copy button (that is
JavaScript). The Webapp and the hub are inside the app and may use its JS.

### Act A — Invite + claim (`/claim?t=<invite token>`)

- **Entry:** the invite email (`BRAND.md` §Email) with one single-use link.
- **Claim screen.** Invitation for `<email>` (not “signed in as”:
  there is no HQ account). The deck's promise, the key field with the two ways
  to make a key (a key file at `~/.ssh/odile`; a 1Password/Bitwarden item
  served by the SSH agent), the server-parsed fingerprint, the second-copy
  confirm, and the price/ask panel. A quiet link to the demo machine's report.
  The form is **two steps without JavaScript**: the first POST parses the key
  and re-renders the page with its type, fingerprint and the second-copy
  confirm; the second POST, with the confirm, creates the claim. Nothing is
  stored on the first POST.
- **One primary:** **Claim my machine**.
- **States:** unknown token; used token (renders the reserved state, so a closed
  tab is recoverable); malformed key; a private key pasted; a key with options
  or more than one line; the claimed state.
- **Server:** parses the key, stores only the public half and its SHA-256
  fingerprint; the confirming POST creates the claim and marks the token used;
  a replay aborts (the schema's single-use trigger).
- **Copy:** the key is the **boot key**, not the login; the Odile sign-in is set
  at install. The fingerprint matches `ssh-keygen -lf`.
- **Replaces:** prototype screens 01 (Invite), 02 (Claim).

### Act B — Reserve (the same URL, after the claim)

- **Reserved state.** “A machine is reserved for you.” The price and what it
  buys; what it asks of you; **the sample proof**: a link to
  `https://odile.fyi/verify` carrying the demo-scope sentence. In the V0.1
  alpha the payment is a Stripe link sent by email and marked paid by hand; the
  state says so. From M4 `ODL-241` puts the Payment Link and the webhook on
  this page and the primary becomes **Pay $49/month**.
- **One primary (V0.1):** **Open the sample report** — the only action on the
  page. The money action is in the email until M4.
- **States:** reserved → paid → building. “Building” links to `/ready/<slug>`
  once the ready email exists.
- **Why no Pay button now:** Stripe is M4 (`ODL-241`); the alpha is hand-sold
  and Savio marks paid by hand (`docs/MVP-V0.1.md` §6.2). A dead Pay button is
  worse than an honest handoff.
- **Replaces:** prototype screens 03 (Reserve), 04 (Build).

### Act C — Build + ready (`/ready/<slug>`)

- **Entry:** the ready email (`BRAND.md` §Email) and the reserved state.
- **Ready screen.** Served by the HQ route from the tenant row when the
  machine is ready; the slug addresses it. **The building state lives on the
  reserved page** (Act B), so the wait is a state, not a screen. The ready
  email carries the address, the release, the setup token and the link, and
  attaches the recovery kit; the page carries every command, including the
  installer. The setup token is the one value copied from the email (the kit
  carries it too), and the page says so (`BRAND.md` §Email: “the ceremony page
  carries the commands”).
- **One primary:** **Run the verifier** — step 1's command block, first and
  largest.
- **The three gaps** sit above step 1, in the deck's order, inside one
  `<details>` titled “Before you type”.
- **Replaces:** prototype screens 04 (Build), 05 (Ready).

### Act D — Ceremony (the `/ready` checklist)

- **Checklist screen — the same page, the four steps as native `<details>`.**
  Only step 1 is open on load. Each step is one copy block:
  1. **Verify** (laptop): download the verifier, check its hash, run it, wait
     for PASS; compare the first-connect host-key fingerprint.
  2. **Encrypt** (SSH to the initramfs): `encrypt`, six lowercase words, twice;
     reconnect, `unlock`, type the passphrase; the machine boots.
  3. **Install** (SSH): create `recovery-kit.json` from the kit's block in
     the root shell, then run the signed installer with it; the setup token is
     the value you copy from the ready email. Set the Odile sign-in; it prints
     the URL.
  4. **Recovery file**: `scp` it off, `shred` the copy on the machine.
- **One primary:** **Run the verifier** — step 1's block, first and largest;
  **Open the terminal** is the quiet link from step 1 to step 2, not a second
  primary.
- **The host-key stop sign** is its own `<details>`: “don't type the passphrase
  on a changed host key.”
- **No checkbox gating.** The prototype's recovery tick is a JS gate; the page
  uses an imperative sentence instead, because a checkbox that cannot gate
  anything is a lie. The load-bearing moment is the copy-off command and the
  warning, both kept.
- **Replaces:** prototype screen 06 (Terminal).

### Act E — First run (the Webapp's first session)

> **Corrected 22 November 2026 (follow-up to ODL-469):** the ritual ships as
> five questions, not three, and the brief email ships with it. The bullets
> below are the as-shipped record; `skills/odile-first-run/SKILL.md` at `main`
> is the source. PF-05 (§4) and C3 (§6) keep the 9 November decision text with
> their own dated notes.

- **Entry:** the first sign-in at the URL the installer printed.
- **First-run screen — the agent's first turn.** The agent introduces itself as
  Odile, says it runs as `odile` with sudo, and asks **five questions, one per
  message**: what to call you; where you are (a city sets the IANA time zone);
  three things to handle; what time the brief should land, 07:00 local by
  default; and, last, whether it may email the brief too, and to which address.
  After the third answer it writes today's brief **for real**
  (`~/briefs/YYYY-MM-DD.md`, with a fetched fact) while it asks the last two.
  It then schedules one repeat job at the time from answer 4 in the IANA zone
  from answer 2, with the installed sender as the job's last step, and says
  what happens next in three sentences. A yes to email writes
  `~/.hermes/brief.json` (`{"to": "…"}`, mode 0600) on the machine; a no writes
  nothing and the brief stays in `~/briefs/`. Only the brief time has a default.
- **One primary:** **Open today's brief** — today's file, not a promise.
- **Skippable**, writes `onboarded_at`, never nags.
- **Replaces:** prototype screens 07 (First run), 08 (Brief). The brief email
  is shipped: `ODL-235` built the sender, and `ODL-469` wired the sender into
  the tenant and the address question into this ritual.

### Act F — Your machine (`/#/hub`, or the pinned session)

- **Entry:** the pinned sidebar row “Your machine” (`/#/sessions/<id>`); on the
  plugin path also the `/#/hub` row, and both are bookmarkable. The ready
  email carries the app URL, not a session id.
- **Hub screen.** One page, one primary: **Ask the agent** (a new chat). Quiet
  sections: **Workspace** (a new chat / the last sessions),
  **Files** (`#/artifacts`), **Schedule** (`#/cron`), **Check the machine**
  (`/verify`), **If it is waiting** (the unlock command, both key paths, and
  the deck's reboot sentences), **Support** (`help@odile.fyi`, the FAQ at
  `https://odile.fyi/faq`; the tenant does not serve `/faq`).
  The hash routes go through the Webapp's own navigation, not a hard-coded
  URL.
- **The hub is a Webapp plugin page when the page renders, and always a pinned
  “Your machine” session.** The pinned Hermes webapp exposes a `routes`
  contribution area and a `sidebar.nav` area (read in the installed bundle,
  9 November 2026). C4's first step is a one-day spike proving a contributed
  route renders in the browser-hosted Webapp. Independently of the spike, C3's
  first-run skill posts the same six links as a machine card and makes the
  ritual's session the pinned “Your machine” home when the ritual ends — unless
  a session already carries that title, which it leaves alone — so the home
  exists before the page is decided; if the route renders, the page is the
  richer rendering of the same card, and C4 records which shipped.
- **When the machine is waiting at the initramfs the Webapp is down.** The
  unlock email is the state; the hub says so and carries the command for when
  it is up. No per-tenant HQ page in V0.1 (that needs an HQ read credential;
  deferred, §8/PF-03).
- **Replaces:** prototype screens 09 (Workspace), 10 (Verify), 11 (Reboot),
  12 (Support) as separate pages; they become sections and links.

## 6. The card split

Five cards: two re-cuts and three new. All M3, all S or M. This card (ODL-406)
edits no code. C1 and C2 are the same two build cards whether they land on
`ODL-231`/`ODL-232` or on new ids: the old cards are re-cut **in place** only
while they are still open and never started; if either has moved, that card is
recorded as superseded and C1/C2 are seeded under new ids (§6.1). `refresh`
rewrites only a card in `blocked`/`todo`/`ready`/`scheduled`
(`tools/board_sync.py:527`) and writes only the assignee and the body
(`tools/board_sync.py:514-551`); it does not create or remove parent links —
`seed` links only the cards it creates (`tools/board_sync.py:480-492`). The
re-cut's new `depends_on` edges are therefore applied with `kanban_link`
(§6.1). Every CLI mutation in §6.1 runs as
`env -u HERMES_DELEGATED_CHILD_CONTEXT …`: the seeding card is a dispatched
worker and the Kanban CLI refuses to mutate under that marker. A body's
`Depends on:` line is a description; `task_links` is the
dispatcher's gate. The new cards take the next free `ODL-4xx` ids at seeding
(never `ODL-233`); the bodies below are the card bodies.

### C1 — Act A+B, the claim page and the reserved state (`ODL-231`, re-cut or new per §6.1)

- **Milestone:** M3 · **Lane:** frontend · **Size:** M
- **depends_on:** `ODL-220` (claim automation), `ODL-237` (done: the deck's access rows)
- **touches:** `web/claim.html`, `app.py`, `tests/test_claim_page.py`
- **goal:** one no-JS page turns a single-use invite into a claim with the
  boot public key, the fingerprint and the second-copy gate, states the price
  and the ask, and leaves a reserved state the user can reopen.
- **dod:**
  - A valid `ssh-ed25519` or `ssh-rsa` public key creates a claim; the tenant
    is `claimed`; the public key and its SHA-256 fingerprint are stored; the
    private key, a multi-line value, a key with options and a malformed key
    are rejected in place.
  - The fingerprint is shown on a re-render before the claim; the second POST,
    with the second-copy confirm, creates the claim; nothing is stored on the
    first POST.
  - The fingerprint on the page matches `ssh-keygen -lf` on the test laptop.
  - Both key paths are offered as copy-pasteable commands: a key file at
    `~/.ssh/odile` and a 1Password/Bitwarden item served by the SSH agent (the
    commands then omit `-i`). A non-terminal user with 1Password or Bitwarden
    produces a valid public key without a terminal, and the fingerprint
    matches (`docs/backlog.yaml` ODL-231, kept in C1).
  - The second-copy confirm is required **server-side**; there is no
    client-side disabled state (there is no JavaScript).
  - A used token renders the reserved state, not an error; the state says the
    payment link and the recovery kit arrive by email, and links the demo
    machine's report with the demo-scope sentence.
  - No password field, no passkey, no `<script`, no cookie, no third-party
    request; 390 and 1440; keyboard and CSS-disabled read-through.
  - Every claim sentence is in the Act A table of §5; tests cover all
    states; `make check` green.
  - A Designer `Brand: pass` is on the card before the verifier merges,
    naming the surfaces, the states and 390/1440 (`docs/AGENT-ORG.md` G2).

## 7. What this does not change

- **The unit of tenancy** is still one user, one VM, one URL, one bill.
- **The key model:** the boot key is the user's, generated before the claim and
  the only key in the measured command line; the disk passphrase is set at first
  boot; the Odile sign-in is set at install and hashed on the guest. No passkey,
  no HQ account, no escrow.
- **The data path:** browser → guest TLS; guest → NEAR AI's TEE through the
  meter. The claim page carries the invite token and the public key; the ready
  page carries the slug and links the kit; the ready email carries the setup
  token and attaches the kit. HQ stores only hashes of the claim and setup
  tokens (`docs/CLAIMS.md` §1 Data handling) — never a prompt, a file or a
  credential that opens the machine.
- **The activation definition** in `docs/backlog.yaml` meta: claimed + ceremony
  + installed + ritual + one scheduled job delivered.
- **The price** ($49 founding, $12 allowance) and **the claims deck**.
- **No “non-technical” claim.** V0.1 is for people technical enough to
  generate one SSH key and paste a command (`REVIEW-UX-2026-11-07.md` §6.4).
  The claim page offers the vault path (1Password/Bitwarden) as one of two
  ways to make the key, but the ceremony is still terminal commands. The six
  acts remove screens and questions, not the terminal.

## 8. The deferred piece: a per-tenant HQ page

PF-03's “where is my machine?” is answered by the hub when the machine is up
and by the unlock email when it is down. A per-tenant HQ page that shows
“building / waiting / active” would need a read credential at HQ — a token or
magic link, stored hashed, with its own row in the data inventory — and it
would be a second login surface. That is a real change to the “no account at
HQ” story, so it is **not** in the six acts. It can be a M2 card after the
state machine (`ODL-216`) is live; the trigger is a tenant saying the unlock
email was not enough. The hub links the aggregate status page only if
`ODL-239` is actually served (`odile.fyi/status` currently 404s); otherwise it
carries the command and no link.

## 9. The kill criterion

**If one outsider who did not build the flow completes the current linear
ceremony — the ready email, the ceremony guide and the prototype as the map —
unaided in 30 minutes or less at the M1 gate, the six acts are discarded.**

- Measured at the **M1 gate (28 November 2026)** on a freshly provisioned
  tenant; if `ODL-330` provides only one machine, the gate rebuilds the M1
  tenant after Savio's five-day log (or uses the first M2 tenant) and records
  which. The timer starts at the ready email and stops at the first successful
  sign-in; every question the outsider asks is logged as help.
- If the machine tail slips, the reading moves with `ODL-332`; the split is not
  seeded until it is recorded.
- “Discarded” means the split is not applied — `docs/backlog.yaml` is not
  edited, C3–C5 are not seeded, and `ODL-231`/`ODL-232` keep their linear-flow
  bodies — and M3 builds the linear flow from the prototype (claim, ready,
  verify, first run as originally cut). The spec stays as the record of the

## 10. Privacy-first test

The one rule from the UX review stands: no surface says “No one at Odile can
log in” without “to a tenant machine” where a demo is in view. The claim page's

## 11. What we deliberately do not build

- **No Stripe checkout in the six acts.** The alpha's payment is a link sent by
  email and marked paid by hand; `ODL-241` (M4) puts the Payment Link and the
  webhook on the reserve state.
- **No per-tenant HQ dashboard** (§8).
- **No support-grant button** in V0.1's hub; the CLI and the FAQ link are the
  M3 surface, the button is M2 (`ODL-217`).
- **No new auth, no HQ account, no passkey.**
- **No JavaScript on HQ pages.** Native `<details>` covers progressive
  disclosure; there is no copy button.
- **No new claim.** Every privacy, security or reliability sentence is in §5;
  a sentence not there waits for a deck row.
